Azure integration platform · explained simply

How the platform is orchestrated

How our APIs and the business systems behind them run in Azure. Think of it as a building with three parts: the rules and keys (who may change what), the front door (where every request is checked) and the workshop (where the business services do the work). The business services work together through events: they announce what happened instead of calling each other. Everything is private by default, nothing uses stored passwords, and AI assistants follow the same rules as everyone else.

View 1

Big picture: who does what

One team sets the rules, two areas are built from blueprints, and each business team runs its own service.

flowchart LR
  USERS["People, partners<br/>and AI assistants"]
  DOOR["Front door<br/>apixp"]
  WORK["Workshop<br/>intapp"]
  TEAMS["Team projects<br/>product · orders · logistics"]
  RULES["Rules and keys<br/>platform-governance"]
  USERS -- "make requests" --> DOOR
  DOOR -- "passes them on privately" --> WORK
  TEAMS -- "run their services in" --> WORK
  TEAMS -- "publish their APIs on" --> DOOR
  RULES -. "sets up and controls" .-> DOOR
  RULES -. "sets up and controls" .-> WORK
  RULES -. "gives each team its keys" .-> TEAMS

In plain words

  • There are two separate areas in Azure: the front door (apixp), where requests come in, and the workshop (intapp), where the work happens. A problem in one doesn't spill into the other.
  • Everything is built from code "blueprints" (Terraform), so dev, test, pre-production and production all look the same.
  • Each business area (products, orders, logistics) has its own team project and can release without waiting for the others.
  • Everything is named the same way, so anyone can tell what something is and where it lives.
Why not put everything in one place?

Different teams work at different speeds and need different access. Splitting keeps each team in its own lane and limits the damage of a mistake.

View 2

Build order: like building a house

We build in a fixed order: foundations first, then the rooms, then the furniture.

flowchart LR
  S1["1<br/>Safe place for<br/>the blueprints"] --> S2["2<br/>Rules<br/>and keys"]
  S2 --> S3["3<br/>Private<br/>network"]
  S3 --> S4["4<br/>Front door and<br/>message system"]
  S4 --> S5["5<br/>Connect the<br/>two areas"]
  S5 --> S6["6<br/>Team<br/>services"]
  S6 --> REL["Release: dev → test → pre-prod → prod<br/>the last two need a person to approve"]

In plain words

  • Once: set up a safe place to store the blueprints.
  • Rules and keys: governance creates the spaces and gives each team's automation its own keys.
  • Roads and walls: the private network in both areas.
  • Shared services: the front door and the message system.
  • Connect: link the two areas privately.
  • Business services: each team ships its service. Changes move dev → test → pre-production → production, and the last two need a person to approve.
What stops a bad change reaching production?

It has to pass through every earlier stage first, and pre-production and production both need a named reviewer to approve it.

Same shape, bigger sizes: API Management Premium spread across 3 availability zones, larger plans (P1v3), more Service Bus capacity, zone-redundant storage, and every release needs a reviewer's approval.

View 4

Automation with no passwords

Our automation has no stored passwords. It proves who it is each time and only gets the keys for one job.

sequenceDiagram
  participant GH as GitHub Actions job
  participant Entra as Entra ID
  participant State as Terraform state
  participant ARM as Azure Resource Manager
  GH->>Entra: OIDC token, subject repo:org/intapp-infra:environment:dev
  Entra->>Entra: match federated credential on id-gh-intapp-infra-dev
  Entra-->>GH: access token for that managed identity
  GH->>State: read and write its own state container only
  GH->>ARM: plan and apply on its landing RGs only
  ARM-->>GH: role assignments allowed only for delegable roles (ABAC)

In plain words

  • Each deployment gets a short-lived pass, valid for minutes, for one project and one environment.
  • A test deployment cannot use the production pass.
  • Even when signed in, it can only change its own areas.
  • It can only hand out a short, pre-approved list of permissions, never admin rights.
Why does this matter?

Leaked passwords are one of the most common ways cloud systems are breached. With nothing stored, there is nothing to leak or rotate.

How do you stop someone giving themselves admin rights?

The automation may only hand out a fixed list of low-risk permissions. Azure refuses anything else.

Is the front door on the internet?

If one service is busy or down, its messages wait safely instead of failing. Teams can change their service without breaking the others.

Services announce what happened, and anyone who needs to know listens. Nobody calls anybody directly.

In plain words

  • Services announce what happened ("order accepted", "stock changed") instead of calling each other.
  • Each business area owns one channel (a topic) and is the only one allowed to post on it.
  • Anyone who cares subscribes. Adding a new listener, such as a new reporting feed, needs no change to the sender.
  • Each listener gets its own filtered copy and its own "problem tray", so one slow or broken listener never holds up the others.
  • Channels, filters and permissions are all generated from one file, so this picture is exactly what is deployed.
How is this different from an API?

An API is for asking a question now ("what's the stock?"). An event tells everyone that something happened. We use both: APIs at the front door, events between the services.

View 9

Event-driven: never lose a message

A change and its announcement are saved together, sent in order, processed once, and parked safely if something goes wrong.

flowchart LR
  REQ["Request or command<br/>e.g. place order"] --> SVC["Domain service"]
  SVC -- "one unit of work" --> DB[("Order + outbox entry<br/>saved together")]
  DISP["Outbox dispatcher<br/>runs every 10 s"] -- "reads pending" --> DB
  DISP -- "MessageId = event id<br/>SessionId = OrderId" --> T["Topic<br/>duplicate detection"]
  T --> SUB["Filtered subscription<br/>sessions keep order"]
  SUB --> CONS["Listener<br/>skips repeats"]
  SUB -- "still failing after retries" --> DLQ["Dead-letter queue<br/>alert + replay"]
  CONTRACT["Contracts in Git<br/>AsyncAPI + JSON Schema"] -. "same envelope for every event" .-> T

In plain words

  • The change and its announcement are saved together (the "outbox"), so you never get one without the other.
  • A background job sends the announcements in order. If the message system is down, it simply tries again later.
  • Every message has a unique ID, so if it arrives twice it is only acted on once.
  • Messages about the same order or book are kept in sequence.
  • If a message keeps failing, it is set aside with the reason, an alert goes out, and it can be replayed after a fix.
  • Every event uses one agreed format, written down in Git. Changes only ever add fields.
What happens to listeners when an event changes?

We only add fields, so existing listeners keep working. A breaking change becomes a new version that runs alongside the old one until everyone has moved over.

View 10

One order, start to finish

The event-driven design in action: a retailer's order passes through three teams without any of them waiting for or calling each other.

sequenceDiagram
  autonumber
  participant EDI as EDI inbound adapter
  participant ORD as Orders service
  participant SB as Service Bus
  participant LOG as Logistics service
  participant BY as Blue Yonder adapter
  participant OUT as EDI outbound adapter
  EDI->>SB: PlaceOrder to order.commands
  SB->>ORD: PlaceOrder, session = OrderId
  ORD->>ORD: save order + outbox in one unit of work
  ORD->>SB: OrderReceived, OrderAccepted to order.events
  SB->>LOG: OrderAccepted via logistics-allocation
  LOG->>SB: OrderAllocated + StockChanged to logistics.events
  BY->>LOG: dispatchShipment, warehouse has shipped
  LOG->>SB: ShipmentDispatched to logistics.events
  SB->>ORD: ShipmentDispatched via orders-status
  SB->>OUT: ShipmentDispatched via edi-despatch-advice

In plain words

  • 1–2: the retailer's order arrives and the Orders service picks it up.
  • 3–4: Orders saves it and announces "order accepted".
  • 5–6: Logistics hears that and reserves the stock.
  • 7–8: when the warehouse ships, Logistics announces "shipped".
  • 9–10: Orders marks the order as dispatched, and the retailer gets a despatch note.
  • Ground rules: only the owner announces its own events, every message uses one standard format, duplicates are ignored, and failures are retried and then set aside for a person to check.
What if the message system is down?

The order and its announcement are saved together. The announcement goes out as soon as the system is back, so nothing is lost.

View 11

AI assistants follow the same rules

AI assistants go through the same front door and the same checks as everyone else, and can only do what the person asking could do.

sequenceDiagram
  autonumber
  actor Rep as Sales rep
  participant Agent as Copilot Studio agent
  participant APIM as APIM MCP server
  participant Fn as Logistics Function App
  participant APIC as API Center
  Rep->>Agent: What is the stock for ISBN 9780141036144?
  Agent->>APIM: MCP call getStock with the rep's Entra token
  APIM->>APIM: guardrails: token G2, approved client G1, rate limit, audit G5
  APIM->>Fn: GET stock via private endpoint + function key
  Fn-->>APIM: available, reserved, free
  APIM-->>Agent: tool result, outcome audited
  Agent-->>Rep: answer
  Note over APIC: only APIs and MCP servers registered here are approved, G1 G6 G7

In plain words

  • A sales rep asks an AI assistant: "What's the stock for this book?"
  • The assistant uses the rep's own login, so it can't see more than the rep can.
  • Only approved assistants and approved tools are allowed. They are listed in a catalogue (API Center).
  • Tools start read-only. Anything that changes data needs explicit human approval first.
  • Every request is logged: who asked, which assistant, which tool, and what happened.
Why not let the AI connect straight to SAP or the database?

That would skip every safety check. Going through the front door means the same rules, limits and audit trail as any other user.

How the projects fit together

The projects don't depend on each other's internals. They share a few agreed facts, like a contract.

flowchart LR
  GOV["platform-governance"] -- "GitHub env vars<br/>client ID · subscriptions · FUNCTION_APP_KEY · policy tokens" --> API["API repo pipeline"]
  APX["apixp-infra state<br/>apim_name · product_ids · api_center"] -- "terraform_remote_state" --> API
  INT["intapp-infra state<br/>function_apps by domain"] -- "terraform_remote_state" --> API
  NAME["Shared naming module<br/>prh-type-sub-env-purpose-uks-001"] --> CS["core-services roots"]
  NAME --> APP["application roots<br/>build subnet and DNS IDs by name"]
  YAML["event-domains.yaml"] --> SBT["topics · subscriptions · RBAC"]
  OAS["openapi.yaml"] --> APIT["API · MCP tools · API Center definition"]

In plain words

  • Each infrastructure project publishes a short list of facts (for example, "the front door is called X") that the others read.
  • One naming pattern means projects can find each other's parts without asking.
  • Two simple files drive most changes: one lists the business messages, one describes each API.
How do you add a new business area?

Add it to a few settings files and copy an existing team project. The front door doesn't need to change.
