Azure integration platform · Terraform · GitHub Actions

How the platform is orchestrated

Three platform repos and one repo per business domain. Governance decides who may deploy what and where. apixp is the front door: APIM, API Center and shared services. intapp hosts the domain services and the Service Bus event backbone. Everything is private by default, every pipeline signs in without secrets, and AI agents use the same governed APIs as everything else.

Governance sets the guardrails, the two infra repos build the landing zones, and each domain repo deploys its own code and API into them.

Talking points

  • Two subscriptions with a clear split: apixp exposes, intapp runs. The blast radius of a change stays in one place.
  • Each infra repo has two Terraform roots: core-services (network in an existing VNet) and an application root on top.
  • Domain teams own their repo end to end: code, OpenAPI contract, policies and MCP tools. Adding an API doesn't touch apixp-infra.
  • Naming is one convention everywhere: prh-<type>-<sub>-<env>-<purpose>-uks-001.
Why separate repos instead of one mono-repo?

Different owners, cadence and permissions. Each repo's pipeline identity can only touch its own resource groups, so a domain team can't change the gateway and the platform team can't change domain code.

Delivery order: how the pipelines chain

Bootstrap once, then governance, then network, then platform services, then the domains, promoted dev to prod.

flowchart TD
  B["1 · Bootstrap, local, once<br/>state storage · governance identity"] --> G["2 · platform-governance<br/>RGs · identities · RBAC · PIM · GitHub envs"]
  G --> C1["3a · apixp core-services<br/>subnets on existing VNet"]
  G --> C2["3b · intapp core-services<br/>subnets · central DNS zones"]
  C1 --> P1["4a · apixp integration-platform<br/>APIM · API Center · shared services"]
  C2 --> P2["4b · intapp integration-applications<br/>Service Bus · domain Function Apps"]
  P1 --> S["5 · Second pass<br/>VNet peering + DNS links both ways"]
  P2 --> S
  S --> API["6 · API repos<br/>code to Function App<br/>API + MCP server to APIM<br/>register in API Center"]
  API --> PROM["dev → test → pre → prod<br/>pre and prod wait for reviewers"]

Talking points

  • Bootstrap is the only manual step: it creates state storage and the identity governance runs as.
  • Governance writes each repo's GitHub environment variables, so nobody copies client IDs by hand.
  • Each infra pipeline runs core-services then the application root in one job, per environment.
  • Peering is a deliberate second pass: each side owns its half, so neither repo needs rights to create the other's VNet.
  • PRs plan every environment and post the plan as a comment; merging to main applies in order.
What happens if the network layer changes in the same PR as an app?

The application roots build subnet and DNS zone IDs from the shared naming module instead of reading state, so they still plan; on apply, core-services always runs first.

View 3

Pipeline sign-in: no secrets anywhere

GitHub exchanges an OIDC token for a managed identity that is federated to exactly one repo and one environment.

sequenceDiagram
  participant GH as GitHub Actions job
  participant Entra as Entra ID
  participant State as Terraform state
  participant ARM as Azure Resource Manager
  GH->>Entra: OIDC token, subject repo:org/intapp-infra:environment:dev
  Entra->>Entra: match federated credential on id-gh-intapp-infra-dev
  Entra-->>GH: access token for that managed identity
  GH->>State: read and write its own state container only
  GH->>ARM: plan and apply on its landing RGs only
  ARM-->>GH: role assignments allowed only for delegable roles (ABAC)

Talking points

  • One user-assigned identity per repo and environment, federated to that GitHub environment. Prod credentials can't be used from a dev job.
  • pre and prod environments can only deploy from protected branches and need reviewer approval.
  • Infra pipelines can grant roles, but an ABAC condition limits them to a short list of data-plane roles, such as Key Vault Secrets User and Service Bus Data Sender.
  • Resource providers are registered by governance, so pipelines need no subscription-level rights.
Why not a service principal with a secret?

A secret can leak and has to be rotated. With federation there is nothing to store, the token lives minutes, and the trust is scoped to repo + environment.

Governance: least privilege by resource group

Every identity, human or pipeline, gets the smallest scope that lets it do its job, and humans have no standing write access.

Talking points

  • Governance creates the landing RGs, so pipelines are scoped to RGs, not subscriptions, and can't create new ones.
  • The VNets are existing and owned by the network team; pipelines only get Network Contributor on that RG to add subnets.
  • A custom "VNet Peering Operator" role lets each side peer and register private endpoints in the other side's DNS zones, and nothing else.
  • People's access is code: change access.yaml in a PR, the plan shows who gains or loses access, merge to apply. Membership is authoritative.
How do you stop a pipeline from granting itself Owner?

It only has Role Based Access Control Administrator with an ABAC condition listing the role definition IDs it may assign. Any other role assignment is denied by Azure.

Talking points

  • Subnets are created in an explicit depends_on chain so operations on the shared VNet never overlap.
  • APIM's route table merges the shared UDR with a direct route for the APIM control plane, so forced tunnelling doesn't break the gateway.
  • The policy layer is platform-owned: global policy plus fragments for auth, rate limit, errors, routing and MCP guardrails.
  • Identities follow the slide: APIM UAMI reads Key Vault, the common-utils UAMI reads config and the routing table, a KQL identity can only read logs.
Why External VNet mode and not Internal?

External keeps a public gateway for partners while every backend stays private. It's one variable (apim_virtual_network_type) if the gateway should go fully private behind a WAF.

intapp: domain services and the event backbone

One resource group, subnet and Function App per business domain, with a shared Service Bus where each domain owns one topic.

    ASP["App Service Plan"] --> FA["Linux Function App<br/>.NET 8 isolated · system identity"]

  end
  FA -- "all outbound via subnet" --> WS
  FA -- "send own topic, receive own subscription" --> SB
  FA -- "Secrets User" --> KV
  FA --> STG
  FA -. "telemetry" .-> LAW
  PE -. "app · storage · KV · SB endpoints" .-> DNS

Talking points

  • Private by default: Function Apps, storage, Key Vault and Service Bus have public access off. APIM reaches apps over peering and private DNS.
  • No connection strings: storage, Service Bus and Key Vault all use the app's managed identity.
  • The backbone topology is one YAML file. Terraform turns it into topics, filtered subscriptions and exactly the RBAC each publisher and consumer needs.
  • intapp owns the central private DNS zones, and apixp's private endpoints register in them too.
Why Service Bus and not Event Grid for this?

We need ordering per order or ISBN (sessions), duplicate detection, dead-lettering and replay. Event Grid is kept as an optional add-on for push-style notifications.

View 7

One order, end to end

A retailer order moves through three domains without any of them calling each other directly.

sequenceDiagram
  autonumber
  participant EDI as EDI inbound adapter
  participant ORD as Orders service
  participant SB as Service Bus
  participant LOG as Logistics service
  participant BY as Blue Yonder adapter
  participant OUT as EDI outbound adapter
  EDI->>SB: PlaceOrder to order.commands
  SB->>ORD: PlaceOrder, session = OrderId
  ORD->>ORD: save order + outbox in one unit of work
  ORD->>SB: OrderReceived, OrderAccepted to order.events
  SB->>LOG: OrderAccepted via logistics-allocation
  LOG->>SB: OrderAllocated + StockChanged to logistics.events
  BY->>LOG: dispatchShipment, warehouse has shipped
  LOG->>SB: ShipmentDispatched to logistics.events
  SB->>ORD: ShipmentDispatched via orders-status
  SB->>OUT: ShipmentDispatched via edi-despatch-advice

Talking points

  • S1 naming: <domain>.events topics, <domain>.commands queues, subscription named for the consumer.
  • S2 ownership: only the owning domain can send to its topic; each consumer can read only its own subscription.
  • S3 envelope: CloudEvents-style body plus an eventType property that subscription filters match on.
  • S4 reliability: transactional outbox, duplicate detection on event ID, sessions for ordering, idempotent consumers, dead-letter then alert.
  • S5 contracts: AsyncAPI and JSON Schema in Git, additive changes only.
What if Service Bus is down when the order is saved?

The event is already in the outbox with the order. The dispatcher retries in order on its next run, so nothing is lost and nothing is published for a change that didn't happen.

View 8

AI agents use the same governed APIs

APIM exposes read-only API operations as MCP tools, so an agent acts as the user through the same checkpoint as every other client.

sequenceDiagram
  autonumber
  actor Rep as Sales rep
  participant Agent as Copilot Studio agent
  participant APIM as APIM MCP server
  participant Fn as Logistics Function App
  participant APIC as API Center
  Rep->>Agent: What is the stock for ISBN 9780141036144?
  Agent->>APIM: MCP call getStock with the rep's Entra token
  APIM->>APIM: guardrails: token G2, approved client G1, rate limit, audit G5
  APIM->>Fn: GET stock via private endpoint + function key
  Fn-->>APIM: available, reserved, free
  APIM-->>Agent: tool result, outcome audited
  Agent-->>Rep: answer
  Note over APIC: only APIs and MCP servers registered here are approved, G1 G6 G7

Talking points

  • G1 only MCP servers in the agents product and registered in API Center; unknown agent apps get 403.
  • G2 the agent passes the user's own token, and the API checks audience and Logistics.Read scope.
  • G3 tools are generated from operations marked in the OpenAPI file; a write tool fails the deploy without explicit approval.
  • G4–G5 inputs are validated against the contract; user, agent, tool and outcome are logged to App Insights.
  • G6–G7 tools are versioned with the API; confidential data needs approval before any tool is exposed.
Why not let the agent call SAP or the database directly?

That's a new point-to-point coupling with no audit or scopes. Going through the domain API reuses its contract, auth, rate limits and logging, and the agent can't do more than the user could.

View 9

How the repos talk to each other

Repos never call each other; they share outputs, a naming convention and GitHub variables.

flowchart LR
  GOV["platform-governance"] -- "GitHub env vars<br/>client ID · subscriptions · FUNCTION_APP_KEY · policy tokens" --> API["API repo pipeline"]
  APX["apixp-infra state<br/>apim_name · product_ids · api_center"] -- "terraform_remote_state" --> API
  INT["intapp-infra state<br/>function_apps by domain"] -- "terraform_remote_state" --> API
  NAME["Shared naming module<br/>prh-type-sub-env-purpose-uks-001"] --> CS["core-services roots"]
  NAME --> APP["application roots<br/>build subnet and DNS IDs by name"]
  YAML["event-domains.yaml"] --> SBT["topics · subscriptions · RBAC"]
  OAS["openapi.yaml"] --> APIT["API · MCP tools · API Center definition"]

Talking points

  • Terraform outputs are treated as a contract: the API repos read only a few named outputs, so the infra can change underneath them.
  • Two files drive most of the platform: event-domains.yaml for messaging and each repo's openapi.yaml for APIs and tools.
  • Policy values per environment come from GitHub variables written by governance and are replaced at deploy time; secrets stay in Key Vault.
How do you add a new domain?

Add a subnet and a workload entry in intapp-infra, the domain to governance, its topic to event-domains.yaml, then copy an API repo. No change to apixp-infra.

Names follow the platform convention (for example prh-rg-intapp-dev-orders-uks-001). Diagrams describe the repos as built; MCP servers use APIM's preview API.
